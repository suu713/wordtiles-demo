# 原包棋盘行方向核查

结论：用户提供的 Word Tiles 1.4.0 安装包，棋盘数据按**从下往上**的行顺序存储；每行内部从左往右。网页此前把数据第一行当成最上面一行，漏了坐标方向转换，所以只出现上下颠倒。关卡文件的提取内容没有改错。

## 策划可以这样理解

原游戏把棋盘左下角当作起点：先写最下面一行，再写中间一行，最后写最上面一行。网页通常从左上角开始排格子。把同一份文字直接按网页习惯排，就会把上下两行对调，中间和每行左右顺序仍然一样。

英语主线第 1 关，原 ID 为 191596，文件里的字母是 `OBE,JIC,SUN`：

| 数据位置 | 原手机游戏里应在的位置 | 字母 |
|---|---|---|
| 第一段，第 0 行 | 最下面 | O B E |
| 第二段，第 1 行 | 中间 | J I C |
| 第三段，第 2 行 | 最上面 | S U N |

所以手机画面从上往下应该是：

```text
S U N
J I C
O B E
```

这属于固定的坐标约定。已核查的建棋盘代码按行号直接放置，没有随机上下翻转步骤。

## 修正方式

算法1现在按原手机游戏的方向显示。原始字母、格子编号、目标参考路径、反算次数和已导出的 JSON 格式都保留，仅把格子放到正确的屏幕行。鼠标拖动、触摸、提示线和键盘上下方向使用同一套显示位置。算法2继续按原算法包的从上往下顺序显示，seed 20261010 的样例不变。

不使用 CSS 整张画面翻转，字母、按钮和目标不会倒置；不重新挑选目标消耗集合，也不修改词库。

## 核查依据

直接读取用户提供的 XAPK，核对 `assets/Levels/english/191596.level` 的 JSON 与网页保留的原始数据完全一致。静态分析包内 Unity IL2CPP 代码，未安装或运行 Android 程序。

- `GridManager.CreateGrid`（`0xf6a010`）：按逗号拆分行，直接读取第 y 行第 x 个字符；格子局部位置为 `(x × 横向间距, y × 纵向间距, 0)`。
- `GridLayoutRuleset.GetRuleset`（`0xf44a60`）：两行棋盘的纵向间距为正 `1.1`，三行及以上为正 `1.0`，行号越大，显示位置越高。
- 位置设置调用最终转到 `UnityEngine.Transform.set_localPosition`（`0x315b364`）。
- `LevelDataExtensions.TryGetLetterAt`（`0xe84d38`）：同样直接读取拆分后的 `rows[y][x]`。
- `GridManager.GetGridTopY`（`0xf7233c`）：顶部位置按 `棋盘位置 + (高度 − 1) × 正纵向间距 + 半个格子尺寸` 计算，进一步说明最后一行才是顶行。
- `ApplyBoardLayoutPositions`（`0xf6b520`）：平移棋盘使它居中，没有把行次序反转。

详细文件校验值、常量和关卡例子见 [apk-grid-orientation.json](./apk-grid-orientation.json)。复核脚本是 `scripts/probe-apk-orientation.py`，沿用项目已有的静态 APK 分析工具。

核查范围为这份安装包的 1.4.0 版本；没有使用实体手机截图逐关对比。网页回归验证包括第1关的实际屏幕行次、键盘上下移动、鼠标/触摸找词、JSON 保持原样以及两套算法的完整验收。
